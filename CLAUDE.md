# CLAUDE.md — Engineering conventions for Weddly

This file tells Claude Code how to work in this repo. The product spec is in [docs/blueprint.md](./docs/blueprint.md).

## Commands

```bash
bun install           # install workspace deps
bun run dev           # backend + frontend in watch mode
bun run dev:backend   # just the API
bun run dev:frontend  # just Vite
bun run typecheck     # both tsc passes
bun run test          # E2E suite
bun run lint:fix      # Biome format + autofix
bun run build         # Vite build to frontend/dist
bun run setup:hooks   # one-time per clone — installs git hooks
```

**When a backend change doesn't show up in the dev app, check the server's age before you debug the code.** A long-lived `bun --watch src/server.ts` can lose its file watcher and go on serving whatever it loaded days ago, which reads exactly like a broken change. `curl -s localhost:8787/api/health/deep` reports `uptime_s`; anything in the tens of thousands means the process predates your edit. Same symptom from a different angle: several `bun --watch src/server.ts` processes can be alive at once while only one holds 8787 (`lsof -nP -iTCP:8787 -sTCP:LISTEN` names it), so killing "the dev server" may leave the one that was actually answering. Kill the listener, start one, move on.

## Architecture

```
React (frontend/src)
  → endpoints.ts (single typed API client)
  → fetch JSON
  → Bun + custom router (backend/src)
  → routes/ (thin) → domain/ (thick) using lib/ (infra)
  → bun:sqlite (data/weddly.db locally, /data/weddly.db in prod)
```

- **One file per feature in `backend/src/routes/`.** Each exports `registerXRoutes(router)`. Adding a feature = new file + one register call in `server.ts`.
- **Wedding-domain logic in `backend/src/domain/`.** Mappers (`toCouple`, `toGuest`), per-aggregate helpers (`getCoupleForUser`, `purgeOneCouple`, `renderSeatingChartPdf`), invite codes, supplier directory data.
- **Generic infra in `backend/src/lib/`.** App-agnostic plumbing: `http` (router/Ctx/HttpError), `logger`, `observability` (Sentry), `mailer`, `audit`, `csv`, `rate_limit`. Domain code imports from `lib/`; `lib/` never imports from `domain/`.
- **Types contract in `shared/`.** `shared/types.ts` is the default; split into a per-domain module (e.g. `shared/suppliers.ts`) only when the cluster is large enough to stand alone. Both sides import via `@shared/*`. Backend mappers convert `*Row` → DTO. No runtime validation library — TypeScript is the contract.
- **One API client.** `frontend/src/lib/endpoints.ts` wraps every HTTP call (`coupleApi.create()`, `guestApi.list()`). Components never `fetch` directly.

## Domain model

See [docs/blueprint.md](./docs/blueprint.md#domain-primitives-v1) for the full table list. Highlights:

- **`couples`** is the workspace. Every protected query is scoped by `couple_id` derived from the session.
- **Money is integer Forint.** No floats. `formatHuf(cents)` for display.
- **Audit log is append-only.** Never UPDATE or DELETE rows in `audit_log`.
- **Schema is additive only.** New columns via `addColumnIfMissing(table, column, ddl)` in `db.ts`.
- **The sidebar marks what the couple has never opened.** `users.visited_nav` (JSON array of `/app/...` paths, union-only via `POST /api/auth/nav-visited`) drives the muted label + brass dot on every unvisited rail row, phone tab, and More-sheet tile; landing on the page clears it. Server-side rather than localStorage for the same reason as `share_prompt_seen_at` — a new device must not re-nudge a couple who has used the workspace for months. The dashboard is never marked, and planners-in-a-client-workspace / the admin rail are excluded. Adding a nav destination needs nothing extra: `matchNavDestination` in `AppShell.tsx` derives the key from `ITEMS`. Covered by `backend/tests/api/nav_visited.e2e.test.ts`.
- **A vendor's weekly availability is TWO shapes of one thing, and one of them is derived.** `vendor_working_hours` holds the intervals the vendor edits at `/vendor/settings/schedule` (Munkarend, Calendly-shaped: named schedule, circular day toggle, from-to pairs, add-block + copy-to-days glyphs). `vendor_availability_settings.weekdays` is the DAY-LEVEL MIRROR of those intervals (a weekday with at least one interval is a working day), and it stays what every couple-facing read consults: the public busy calendar, `next_available`, the directory's date filter. Rules worth not re-deriving:
  - **`setVendorSchedule` is the only writer of either**, in one transaction, which is what makes the mirror unable to drift. Both PUT shapes on `/api/vendor/availability/me/pattern` funnel through it, including the pre-hours `{weekdays}` body (its days become whole working days).
  - **No interval rows means "never opened the editor", not "works no hours".** That vendor's schedule is synthesized from `weekdays` as whole days (`hoursFromWeekdays`), which is lossless and is why hours needed no migration.
  - **An empty week is a 400, not a coercion.** A junk weekday list degrades to "every day" on purpose; an emptied hour editor has no such reading, and silently storing "never available" would drop the vendor out of every date-filtered search.
  - **`vendor_unavailable_dates` is still the whole exception layer, in both directions**, and `VendorAvailabilityView.open_dates` is the direction nothing used to read back: an "exceptionally working" day was invisible in the vendor's own UI and could only be undone by blocking the day.
  - Covered by `backend/tests/api/vendor_availability_pattern.e2e.test.ts`.
- **One business is one card: `couple_suppliers.listing_id` binds a private row to the directory.** Four forms let a couple type a vendor name (the DIY modal, the guest-page venue picker, the planning pipeline, `BookedSupplierCard`) and every one of them POSTs `/api/couple-suppliers`, so the "is this already on Weddly?" question is answered THERE (`findDirectoryTwinByName`, folded name, category-scoped then cross-category exact) rather than in each page's own copy of the directory — a fifth form gets the rule for free. Rules worth not re-deriving:
  - **The client-side `findSupplierTwins` notice is the friendly half, not the gate.** It can only ask about the slice of the directory the page loaded; the server refuses with `409 already_listed` + the listing.
  - **`confirm_not_listed` must keep existing.** Folding drops the town, so a Malom Étterem in Szentendre and another in Eger fold to one string. A couple SHOWN the match and answering "different vendor" gets through, and the answer persists in `not_listed_confirmed` so the card doesn't re-ask on every load. What the guard stops is the silent duplicate, never a couple who looked.
  - **Adopting is non-destructive** (`POST /api/couple-suppliers/:id/adopt`, server re-derives the target so a bad id can't bind the wrong vendor). The row keeps notes, price, mirrored budget line and payment schedule — `supplier_installments` FKs to `couple_suppliers` and a listing has nowhere to put them — and only stops being its own business: the category pick moves to the listing and the price mirrors into `couple_supplier_costs`.
  - **A new business gets LISTED**, published to `community_suppliers` (status `pending`, the ordinary admin queue) and bound, which is what makes it reachable by the claim-invite campaign. It lands pending on purpose: that gate is the only thing between a logged-in couple and the public directory, and releasing it from there is also what mails the vendor their claim link.
  - **The location floor (`isPublishableToDirectory`: city or address) is what keeps private rows private.** A card needs a place to be, and the DIY form collects no address/phone/email at all, so "Anyu főztje" can never reach the bar. Publishing also re-checks pending listings (`includePending`) so two couples adding one new vendor join one queued row.
  - The couple's own card is the SAME card as a listing (hero block, meta line); the sage tint and the "Yours" pill are the only marks of difference. Covered by `backend/tests/api/couple_supplier_directory_bind.e2e.test.ts`.
- **Weddly Points is TWO engines with one rulebook, and a planner is not a vendor account.** `shared/vendor_points.ts` + `domain/vendor_points.ts` key on `vendor_accounts.id`; the planner twin (`shared/planner_points.ts`, `domain/planner_points.ts`, `planner_points_ledger` / `planner_event_outbox`, `GET /api/planner/points`) key on `users.id`, which is why the tables are a parallel pair rather than an owner column. Rules worth not re-deriving, and they apply to BOTH sides:
  - **The ledger is the only truth and the only thing written.** Totals, tiers and standings are derived by replaying it; there is deliberately no counter on the row, because a drifted gamification total is unfixable without an audit trail nobody kept. Feature code NEVER awards: it calls `emitVendorEvent` / `emitPlannerEvent` inside its own transaction and the worker applies the rules, so reviews code stays reviews code.
  - **A `dedupe_key` names the OCCURRENCE, not the attempt** (`review:412`, `client:88`), which is what makes a double delivery, a manual replay and the boot backfill the same single row, and therefore what makes the backfill safe on every boot. Caps are evaluated against the ledger at award time so a replay can never launder past one.
  - **Nothing is ever awarded for a star VALUE.** Collecting a review earns; 5 vs 3 stars changes nothing, and `rating` is not even SELECTed in the rule. Paying for good ratings is how a marketplace buys itself a fake reputation.
  - **Every rule re-reads its own subject** rather than trusting the outbox payload (published + not soft-deleted + the subject really is this owner; a `planner_clients` link still active; `couples.is_demo = 0`, since the demo-seed button inserts live links and the ledger is append-only). An event only records that something was true when it was written.
  - **A perk is only a perk if code enforces it.** The vendor table pays search boost, lead credits and a subscription discount; the planner table has exactly TWO fields (`directory_boost`, `profile_badge`) because those are the only two anything enforces, and inventing a third would make the tier a sticker. The planner boost sorts BELOW the admin `planner_verified` flag: points must never outrank a human's trust decision. The unlock copy shows the DELTA against the tier already held, or a Gold holder is promised a badge they are already wearing.
  - **A standing is scoped to a pool the owner competes in and can act on**: the vendor's own category, the planner's own country (whole directory pool when they set none). Both pools are the DIRECTORY visibility predicate (planner side: `PLANNER_DIRECTORY_VISIBLE_SQL`, single-sourced in `domain/planner_profile.ts` and read by the list, the detail and the rank), because a place counted against profiles no couple can reach is a place against nobody. Ties SHARE a place, and a pool of one returns null rather than "1st of 1".
  - **Profile milestones are permanent and read the SAME checklist the UI draws.** `plannerChecklistCompleteness` feeds the settings ring and the payout, so "71% done" and the points can never tell two stories; deleting a photo later does not claw points back, because a bar that goes backwards reads as punishment for editing your own page. A checklist step with no editor anywhere is unearnable points (that was `planner_styles` until the account form got its capped three-chip picker), so a new step needs a home in the same commit.
  - Covered by `backend/tests/api/planner_points.e2e.test.ts` and `vendor_points.e2e.test.ts`.
- **A couple's review and inquiry must reach the vendor they are about.** Both broke at once in July 2026 and neither raised an error anywhere, so these are the invariants, not the implementation notes (audit: commits `8508a5ef`, `c09e8e4e`):
  - **The editorial voice is OPT-IN** (`as_editorial === true`), and an editorial review is published unless explicitly drafted. It used to be opt-out, so any caller that merely omitted the field turned an admin's ordinary 5 stars into "Weddly editors" AND a draft. `published` gates the supplier list, `supplier_aggregates`, the admin counters and the vendor's own `/vendor/reviews` simultaneously, while an admin's read passes `includeUnpublished`, so the author saw their review and literally nobody else did. A draft has **no queue anywhere in admin** (`listFlaggedReviews` filters `flagged = 1`, never `published = 0`), which is why "live unless asked otherwise" is the only safe default.
  - **Outreach delivery does NOT consult entitlement.** The PRO gate belongs on `bookable` (`getAvailability`, the couple's date-picker booking), never on writing the row: the check used to sit in `deliverInquiryFromOutreach` and a FREE-plan vendor's lead was not deferred but DESTROYED, unrecoverable after upgrading, while the couple was toasted "sent" and the vendor was mailed a link to a dashboard with nothing on it. `createBooking`'s `allowUnentitled` is what the outreach path passes; the admin booking route deliberately leaves it off. The basic client list is FREE by design, so the vendor can read what lands.
  - **`supplier_reviews.supplier_id` is bare TEXT with no FK, so canonicalise at the route boundary** (`pathSupplierId`). Every "collect reviews" link is the pretty form (`/vendors/magyar-foto-v12`), so a review written from the link the vendor hands out would key on the slug: invisible to their own page, the aggregate, the admin counters and Weddly Points, yet visible on the page it was written from, which is what makes it invisible as a bug too.
  - **`buildSupplierDetail` keys every lookup on `base.id`, never the path segment.** It resolved the id and then queried photos/reviews/availability/videos/packages/comments with the raw param, so the pretty URL served `bookable:false` and empty everything: the vendor's own share link was the one that looked abandoned.
  - **`outreach_messages.booking_id` is the link between a message and the inquiry it became**, and the idempotency key for both `replayOutreachForListing` (claim-complete hands over the couples who wrote BEFORE the account existed, since `vendor_account_id` is frozen at insert) and `scripts/backfill_outreach_inquiries.ts`. It also drives `OutreachMessage.delivery`, so the couple is told "in their Weddly inbox" vs "emailed", rather than one "sent" that meant four things.
  - **Register refuses an unclaimed directory twin** (`assertNoUnclaimedDirectoryTwin`) and routes to the claim flow, which mails the listing's own `contact_email` as proof. Binding the card at register time would hand anyone the listing of any business we show. A CLAIMED match is logged and allowed through: refusing a real namesake is worse than a duplicate.
  - Covered by `outreach_vendor_inquiry`, `supplier_reviews_open`, `public_vendor`, `vendor_register` e2e suites.

## Auth

- Argon2id via `Bun.password.hash` / `verify`.
- Sessions are opaque random ids + HMAC-SHA256 sigs stored in the `sessions` table — **no JWT**. Format: `Authorization: Bearer {id}.{sig}`.
- `users.status = "active" | "suspended"` is checked on every token verify so suspensions take immediate effect.
- Production refuses to boot without a strong `JWT_SECRET`.
- **Email verification is a HARD gate, and a couples signup has no `users` row until it passes.** `POST /api/auth/register` writes a `pending_signups` row (`domain/pending_signups.ts`) and returns **202** `{pending, email}` — no user, no session. `POST /api/auth/verify/:token` then mints the account (`verified_email=1`) and returns **201** with its first `AuthSession`; that click is the only way a couples account is born. Rationale: an unverified account could never log in anyway (the gate in `handleLogin`), so the row was dead weight that cluttered admin and squatted its address against `users.email UNIQUE`. Re-registering a pending address **overwrites** it (no 409) so an honest re-try always works; only a real verified account 409s. Unclicked rows expire after `PENDING_SIGNUP_TTL_MS` (7 days, matches `VERIFY_TTL_MS`) and are swept hourly by `purgeExpiredPendingSignups`.
- **Everything keyed to a new user_id happens at verify, not register** — `promotePendingSignup` replays the acquisition snapshot, planner-waitlist grant (`grantPlannerAccount`+`initPlannerBilling`), planner-invite rebind, audit, and growth events. GDPR consent (`signup_ip`/`signup_user_agent`) records the **register** request, since that's where the box was ticked. When adding a register-time side effect, put it in `promotePendingSignup`, not `handleRegister`.
- **Other account paths are unchanged and do NOT use `pending_signups`:** OAuth (Google/Apple) is provider-attested → `verified_email=1` + session immediately; vendor register creates a real unverified user + `email_verification_tokens`; admin-provisioned planners are deliberately dormant (`verified_email=0, password_set=0`). So `verify/:token` still serves the legacy shape (**200** `{ok:true}`, no session) for any account that already exists.
- **Legacy unverified `users` rows** (vendors, pre-split couples) are scrubbed after 30 days by `purgeStaleUnverifiedSignups` (`domain/purge.ts`). It purges rather than hard-deletes (audit_log is append-only, FKs are ON) and deliberately spares `password_set=0`, planners, vendors, and already-purged rows. Purged tombstones are filtered out of `GET /api/admin/users`.
- **Tests:** use `registerAndVerify(body)` from `tests/helpers.ts` — it returns the old `{status: 201, data: AuthSession}` shape. `verifyUserEmail(email)` is tolerant (pending → legacy → already-verified no-op). Needing a genuinely unverified user means a direct DB insert; register can't produce one.

## Adding a feature

1. **DB change?** Edit `backend/src/schema.sql` for new tables; add `addColumnIfMissing()` calls in `db.ts` for new columns. Never drop or rename.
2. **API endpoint?** Add a procedure in the matching `backend/src/routes/<feature>.ts`. Use `requireAuth(ctx)` for couple-scoped endpoints. Validate input by hand (no Zod). Return `json(toX(row))`.
3. **Shared type?** Add to `shared/types.ts` first. Both sides will pick it up.
4. **Frontend route?** Add a page in `frontend/src/pages/<feature>/` and a route in `App.tsx`. Wrap protected pages in `<RequireAuth>`. Call the API through `lib/endpoints.ts`.
5. **i18n?** Add keys to `frontend/src/locales/hu.ts` AND `frontend/src/locales/en.ts`. `warnDrift()` flags missing pairs in the console.
6. **Test?** Major-change rule: every new endpoint / schema change / money flow / state machine / auth change ships with E2E coverage in the same commit.

## Code quality

- TypeScript `strict: true` + `noUncheckedIndexedAccess`.
- Biome handles format + lint. Pre-commit runs it on staged files; pre-push runs the full gate against a `git archive` snapshot of HEAD.
- **Never `git stash` or `--no-verify`.** Stash races with concurrent editors; `--no-verify` ships broken code.
- No raw hex colors in components — every value comes from `tailwind.config.js` tokens.
- No `window.confirm` / `alert()` — use the portal-mounted `<ConfirmDialog>` and `useToast()`.
- **Vendor portal (`/vendor/*`): ONE interactive colour.** `blush` (terracotta) marks everything the vendor can act on — CTA fills, the active nav pill, `ProgressRing`'s `active` arc, links, focus rings, selected chips, the stats bars — and nothing else. `steel` is chrome: the header bar and its own hover/focus states, nowhere below it. Everything non-interactive (panels, decorative icons, dividers, quiet labels) is the neutral `paper`/`umber`/`ink` scale, never a tinted wash. Blush therefore CANNOT mean "error" any more: warnings use `amber`, matching the tone table in `ProgressRing`. Exception: `TierBadge`'s blue is the "Kék" tier itself, i.e. data, not decoration. Second exception, owner direction 2026-07-29: **a secondary action standing beside the one blush primary may take a `steel-700` fill** (the header's own colour), rather than a third outline button nobody sees — currently the "Share your listing" CTA in `VendorClientsPage`'s empty state.
- **Vendor portal: NO tinted plate behind an icon** (owner direction 2026-07-29). A decorative icon is drawn on the surface it sits on — `steel-600` (dark: `steel-300`), `strokeWidth={1.5}`, no `rounded-full bg-*` medallion under it. The pale-tint circle had spread to every empty state and section header and reads as a disabled button; the icon alone carries the same meaning at a fraction of the noise. This covers decoration only: an avatar chip (initials are text), a count badge, an interactive control's own fill, and a hover-only background are all still fine. The one ringed circle left is the onboarding success tick, and its fill is gone too — only `ring-sage-400` remains.

## Testing

- **Every test file MUST start with `import "./setup"` (or `"../setup"`, `"../../setup"` depending on depth).** `backend/tests/setup.ts` boots the server and pins the test environment; skipping it means the test fetches against either nothing or, worse, the dev server.
- **`bun test` autoloads `backend/.env` BEFORE `setup.ts` runs.** This is the trap that masked tests-against-the-dev-DB for three days in May 2026. The fix: `setup.ts` uses unconditional `process.env.X = "..."` assignments rather than `??` fallbacks — every dev value that could leak (PORT, DB_PATH, UPLOADS_DIR, RESEND_API_KEY, SENTRY_DSN, AMADEUS_*, SERVE_FRONTEND, EMAIL_FROM, JWT_SECRET, ADMIN_EMAILS, GOOGLE_CLIENT_ID, GOOGLE_TEST_BYPASS, FRONTEND_BASE_URL) gets pinned. If you add a new env var to `config.ts`, pin its test value in `setup.ts` too.
- **Worktree-parallel testing escape hatches: `BUN_TEST_PORT` and `BUN_TEST_DB_PATH`** — set those on the `bun test` invocation to run two checkouts side by side. Plain `PORT`/`DB_PATH` env vars deliberately DON'T win (that's the regression guard from the May 2026 leak).
- **Test DB lives at `./data/test-weddly.db`** and gets `rmSync`'d on every bun-test start. The dev DB at `./data/weddly.db` must never be touched by the suite.
- **Backend test suite:** mostly under `backend/tests/api/<feature>.e2e.test.ts` (per-domain files). The legacy monolithic `backend/tests/e2e.test.ts` is gradually being split into the same per-domain shape — when adding new tests, put them in the per-domain file, not the monolith.
- **Frontend tests run under happy-dom.** Two known limitations: `https://accounts.google.com/gsi/client` script loads are blocked (no impact on test outcome, just noisy logs) and `blob:` URL fetches throw `NotSupportedError`. For HU-locale tests, call `_preloadHuForTests()` in `beforeAll` — the HU translations tree is dynamically imported in production, so synchronous queries against HU labels need the preload.
- **Major-change rule:** every new endpoint / schema change / money flow / state machine / auth change ships with E2E coverage in the same commit.

## Milestone workflow (auto-commit rule)

When a self-contained feature, bug fix, or logical change is complete, follow this sequence before moving on — do not wait for the user to ask:

1. **Run E2E tests** for the affected flow (`bun run test`, or exercise the feature end-to-end if no test covers it).
2. **Fix any issues** the E2E surfaces, then re-run until it passes.
3. **Auto-commit** the milestone with a descriptive message. Push only when the user asks.

A "milestone" is a logical unit of work (Claude's judgment call), not every edited file or every TodoWrite item. Group related changes into one commit. Skip the auto-commit if the change is purely exploratory/WIP and the user has signalled they're still iterating.

## i18n

- **EN is the default EVERYWHERE, on both sides.** Frontend: `detectInitial()` in `lib/i18n.tsx` reads `localStorage["weddly.locale"]` and otherwise returns `"en"` — HU navigators no longer auto-flip, so `navigator.language` decides nothing. SSR: `server.ts` calls `localeForHost(host, null)`, deliberately passing `null` for `Accept-Language`, so a production render is always EN too. `localeForHost` keeps an `Accept-Language` branch, but only tests and internal renders pass one. **The two sides agree by construction, which is what makes it safe to bake body copy into the SSR HTML** — a mismatch between crawled and rendered text reads as cloaking. A user gets HU by picking it in the locale switcher, which persists to localStorage.
- All literals go through `t("path.key")`. No inline strings.
- **Currency follows the user's locale at couple creation** — HU users get HUF, EN users get EUR (overridable in onboarding and via PATCH `/api/couples/current`). Format display amounts with `Intl.NumberFormat(locale === "hu" ? "hu-HU" : "en-US", { style: "currency", currency: couple.currency, maximumFractionDigits: 0 })`.
- Drift detection (`warnDrift()`) on init `console.warn`s missing keys.

## Print export

PDF formats supported in v1: **A4** (seating chart), **A6** (place cards), **A3** (large seating chart). The seating data model must encode positions in millimetres so PDFs render at exact size.

## Deployment

- Single Bun service on Railway. Multi-stage Dockerfile (Bun builder → slim runtime). `WORKDIR /app/backend`. `CMD bun src/server.ts`.
- **Deploy with `scripts/deploy.sh`, never with a bare `railway up`.** `railway up` uploads the current directory as-is, so from the repo root it ships whatever half-written file is on disk at that second. With several sessions editing in parallel that is a race, and it bit us: on 2026-07-20 four production builds failed on TypeScript errors from files another session was mid-write, each failure attributed to whoever happened to commit at that moment. The script exports HEAD (or any ref you pass) into a throwaway git worktree and runs `railway up` from there, so only committed code can go out; it reads project/service/environment from the existing `railway link` and removes the worktree on exit. `scripts/deploy.sh --wait` streams the build and exits non-zero if it fails. Uncommitted work is deliberately left behind (the script prints how many files it skipped) — commit first if you want it deployed.
- `/data` persistent volume holds SQLite + uploads. Without it, redeploy = data loss (unless R2 is on for uploads + backups — see below).
- **Object storage (Cloudflare R2):** uploads + DB backups can live in R2 instead of the `/data` volume. `backend/src/lib/storage.ts` is a Disk|R2 abstraction keyed by the existing relative upload path (`couples/3/photos/5/5.jpg`), so every public `/uploads/<key>` URL and DB-stored value is identical across backends. R2 is selected only when ALL of `R2_ENDPOINT` (`https://<account>.r2.cloudflarestorage.com`), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` are set; otherwise the local-disk fallback runs with zero behaviour change (same "configured?" gate as Stripe — see `R2_ENABLED`). R2 objects are streamed through the app at `/uploads/*` so auth/cache semantics match disk. `domain/backup.ts` (`startBackupWorker`) snapshots SQLite via `VACUUM INTO` and uploads to `backups/` every `R2_BACKUP_INTERVAL_HOURS` (default 24, 0 disables), keeping `R2_BACKUP_RETENTION` (default 14) newest; optional `R2_BACKUP_BUCKET` overrides the bucket. Operator setup (enable R2, create bucket, Railway env): [docs/r2_setup.md](./docs/r2_setup.md). When adding a new R2 env var, pin its test value in `backend/tests/setup.ts` too.
- `VITE_*` env vars are baked at build time. Changing them requires a rebuild.
- Required prod env: `JWT_SECRET`, `FRONTEND_BASE_URL`. Required for email: `RESEND_API_KEY`, `EMAIL_FROM`.
- **Company lookup (planner business auto-fill):** free official registries only (FR SIRENE, NL KVK open data, HU/BE via EU VIES, GR GEMI). Providers in `backend/src/lib/company_lookup/`, factory-gated by country; frontend is registry-agnostic. Only env: `GEMI_API_KEY` (free key, enables Greece; empty = manual entry there). Tests run on fixtures via `COMPANY_LOOKUP_FAKE=1` (pinned in tests/setup.ts). Per-country rationale + how to add a provider: [docs/company_lookup.md](./docs/company_lookup.md).
- **Auto-translate (vendor "Leírás" HU↔EN):** DeepL-backed, gated by `DEEPL_API_KEY` (same "configured?" pattern as Stripe/GEMI). Provider in `backend/src/lib/translate.ts`, route `backend/src/routes/translate.ts` (`GET /api/translate/availability` + auth'd, rate-limited `POST /api/translate`). When the key is unset, availability reports `false` and the frontend hides the Fordítás button — nothing else changes. Free DeepL keys end in `:fx` (→ `api-free.deepl.com`); the lib picks the host automatically. Tests run on a deterministic stub via `DEEPL_FAKE=1` (pinned in `tests/setup.ts` alongside a non-empty `DEEPL_API_KEY`). Covered by `backend/tests/api/translate.e2e.test.ts`. ## Billing / subscriptions

- State machine on `couples` (`shared/billing.ts`): `trialing` (14-day in-app trial, set at onboarding) → `founding` → `active`/`past_due`/`canceled` (driven by the Stripe webhook). Entitlement (edit access) is COMPUTED from status + timestamps in `toCoupleBilling`, never stored — a lapsed couple goes read-only at read-time.
- **Founding (free) goes to the first `FOUNDING_CAP`=200 couples to get BOTH partners in — counted by partner-join, not couple-creation order.** A fresh couple has only partner A, so `initBillingAtOnboarding` (at couple creation in `routes/couples.ts`) always starts the 14-day trial. When partner B joins, `activatePartnerFreeWindow` grants the founding plan (`subscription_status='founding'`, `is_founding_member=1`, `founding_until = partnerFreeWindowEnd(wedding)` — free until the wedding day) **only while founding slots remain**. Eligibility is `foundingSlotsUsed() < FOUNDING_CAP`, where `foundingSlotsUsed` counts granted badges (`is_founding_member=1`, demo + admin-comp `badge=0` excluded) — a slot is spent permanently, so an expired window never frees one. Once the cohort is full, partner-join is a no-op and the couple stays on its trial → paid path. `founding_spots_left` (billing status + admin planner) = `CAP − foundingSlotsUsed()`; `refreshPartnerFreeWindow` re-pins the cohort's window when the wedding date moves. A one-time boot grandfather (`db.ts`) comps every pre-launch couple. Covered by `backend/tests/api/billing.e2e.test.ts`.
- **Never reuse `couples.status` for billing** — that column drives the pause-to-DELETE countdown. A lapsed couple keeps `status='active'` and just loses edit entitlement (data preserved).
- **Additional event-workspaces inherit the owner's FIRST workspace's verdict.** A user's extra events (`POST /api/couples`) don't get their own billing life: `toCoupleBilling` computes status + entitlement from `billingAnchorRow(row)` — the owner's oldest non-deleting workspace (owner = the `owner`-role `couple_member`, fallback `partner_a_id`). So a second event can't mint a fresh trial to dodge a lapsed primary, and a free (trial/founding/paid) primary keeps all the owner's events editable. `is_founding_member` stays per-couple so a secondary never consumes a `FOUNDING_CAP` slot. A primary (its own oldest workspace) anchors to itself — one indexed query, no behaviour change. The admin overview (`owner_user_id` on `AdminCoupleView`) groups the same way: one owner card (its ID) + an "×N" pill, extra events recorded as chips beneath the primary.
- **Founding is a per-OWNER grant, earned ONCE on the anchor.** `activatePartnerFreeWindow` refuses on any non-anchor couple (`isBillingAnchor` guard in `domain/billing.ts`), and the accept-invite paths grant on `billingAnchorRow(couple).id`, not the workspace the invite targeted — so one wedding = at most one `FOUNDING_CAP` slot even across several events, and inviting a partner from a secondary can't mis-grant founding on the wrong workspace.
- **A badge on the wrong workspace is worth nothing, so `reconcileFoundingOnAnchor(ownerUserId)` repairs it.** `toCoupleBilling` reads the ANCHOR, so founding sitting on a secondary delivers no entitlement while still costing a `FOUNDING_CAP` seat — the couple sees "Próba", pays after the trial, and the cohort is one smaller for everyone else. Three ways it happens: the **pre-anchor grant** (before the 2026-07-06 anchor rule) landed on whatever workspace the invite targeted; **pausing the first workspace** promotes the next to anchor and the badge doesn't follow; and a partner arriving via `propagatePartnerToOwnerWorkspaces` fills `partner_b_id` on the anchor but is deliberately billing-neutral. The repair MOVES a stranded badge to the anchor (clearing extras, so it is slot-neutral and can even return seats) and otherwise falls through to the normal `activatePartnerFreeWindow` grant, which keeps the anchor guard + cap. Both accept-invite paths call it instead of granting directly, and `backfillFoundingAnchor()` runs it for every owner at boot (after `partners.backfill`, so an anchor that just gained its `partner_b_id` is eligible on the same pass). Idempotent; logs `founding.anchor_backfill {moved, granted}` only when it changed something. Covered by `backend/tests/api/founding_partner_join.e2e.test.ts`.
- **A couple's invited partner is mirrored across all of the owner's events.** `propagatePartnerToOwnerWorkspaces(ownerId)` (`domain/couples.ts`) runs at both accept-invite paths + create-additional + a boot backfill (`backfillPartnerPropagation`): partner B becomes a `couple_members` member of every non-deleting workspace the owner has, and a NULL `partner_b_id` is filled. It is idempotent, **billing-neutral** (never grants founding — that stays the anchor-only rule above), never moves `users.couple_id`, and skips a workspace already recording a different second person.
- Read-only enforcement is central: `entitlementBlock()` in the `server.ts` request pipeline returns 402 for mutating requests to the workspace edit surfaces (`EDIT_PREFIXES` in `domain/billing.ts`) once a couple lapses. Reads, exports, and recovery flows stay open. Demo couples are always entitled.
- Payment UI is 100% Stripe-hosted (Checkout + Billing Portal) — no card fields in-app, no `@stripe/*` frontend deps.
- **Planner subscriptions** are a parallel system for `user_type='planner'` (a separate aggregate, mirrors vendor billing on the shared `computeEntitlement`). Tiers `starter`/`pro`/`premium` are ALL paid, priced per tier per currency in `shared/planner_billing.ts` (`PLANNER_TIER_PRICE`: EUR 19/29/49, HUF 6900/11900/19900). State lives in `planner_subscriptions` (keyed by user_id); the tier itself stays on `users.planner_plan` (single source of truth, kept in lockstep with `planner_max_clients` by `updatePlannerPlan` — the webhook calls it). First `PLANNER_FOUNDING_CAP`=25 planners get 24 months free (`is_founding_member=1`), granted at `grantPlannerAccount`; everyone after gets a 3-day trial; lapse → hard read-only via `plannerEntitlementBlock` (402, in the `server.ts` chain). Separate webhook endpoint `POST {FRONTEND_BASE_URL}/api/planner/billing/webhook` with its OWN secret `STRIPE_PLANNER_WEBHOOK_SECRET`. Go-live: run `bun backend/scripts/stripe_setup_planner.ts` (test first) to mint 6 prices, set `STRIPE_PRICE_PLANNER_{STARTER,PRO,PREMIUM}_{EUR,HUF}` + the planner webhook secret in Railway. Covered by `backend/tests/api/planner_subscription.e2e.test.ts`. (Note: `backend/tests/api/planner_billing.e2e.test.ts` is the DIFFERENT couple-side "planner-managed + guest-page add-on" suite.)
- **Vendor freemium subscriptions** (users.role='vendor', keyed by `vendor_accounts.id` in `vendor_subscriptions`): first `VENDOR_FOUNDING_CAP`=100 activations get a free founding year; after that the lifecycle is 3-day trial (no card) → card saved via Stripe SETUP-mode Checkout (`POST /api/vendor/billing/setup`, webhook flips status to the vendor-only `lead_window`) → full PRO until the first `VENDOR_FREE_LEAD_CREDITS`=3 couple inquiries are delivered (`recordVendorLeadCredit` in `createBooking`) → the 3rd stamps `billing_starts_at` = 1st of the NEXT month and `ensureVendorScheduledSubscription` creates the Stripe sub with `trial_end` there → active/past_due/canceled via the webhook. The plan is DERIVED (`shared/vendor_plan.ts`): FREE keeps the listing live + editable + the basic client list; PRO gates direct inquiries (`bookable`/createBooking refuse for unentitled vendors), the availability calendar (402 via `vendorEntitlementBlock`), CRM detail, payments, stats. Entitlement math is `computeVendorEntitlement` in `shared/vendor_billing.ts`. Separate webhook `POST {FRONTEND_BASE_URL}/api/vendor/billing/webhook` with its OWN secret `STRIPE_VENDOR_WEBHOOK_SECRET`. Go-live: run `bun backend/scripts/stripe_setup_vendor.ts` (test first), set `STRIPE_PRICE_VENDOR_{EUR,HUF}` + the vendor webhook secret in Railway. Every account-creation path (register, onboarding, claim-complete) grants the sub via `initVendorBilling`; a boot grandfather in `db.ts` comps pre-freemium vendor accounts. Covered by `backend/tests/api/vendor_billing.e2e.test.ts`.
- **The free window is a THREE-rung ladder, resolved by one pure function.** `vendorOfferForSlots(foundingUsed, earlyUsed)` in `shared/vendor_billing.ts`: vendors 1-100 get a year (`is_founding_member=1`), 101-400 get three months (`VENDOR_EARLY_CAP`=300, `is_early_member=1`), 401+ get the 3-day trial. **Both free tiers ride `subscription_status='founding'` + `founding_until`**, so `computeEntitlement` never changed; the badge column is the only discriminator and is also what each cap counts. Slots are spent permanently on grant, so an expired window never frees one. `initVendorBilling` re-resolves the tier INSIDE its transaction, otherwise two concurrent activations could both take the last slot. Anything quoting the offer (billing status, the activation page, the claim page, the invite email) must read `currentVendorOffer()` / the DTO's `offer`, never `founding_spots_left`, which reads 0 while a real three-month offer is still live.
- **Vendor claim-invite campaign** (`domain/vendor_campaign.ts`, `routes/admin_vendor_campaign.ts`, admin UI at `/app/admin/vendor-campaign`): cold outreach to unclaimed `listings`, "a user suggested you, take over your profile". Design points worth not re-litigating:
  - **The CTA pre-mints a `listing_claims` row**, so the link is one click into the claim form rather than the two-mail `/api/vendor/claim/start` hop. `/r/vendor-invite/:token` stamps `clicked_at` and redirects; it **heals an expired claim** by minting a fresh one for the same listing, so an invite link never dead-ends.
  - **One mail per ADDRESS, not per listing** (`UNIQUE(campaign_id, email)`). Targeting also skips addresses that already have a `users` row, because claim-complete 409s on those.
  - **Reminders gate on NOT CLICKED, not NOT OPENED.** Apple MPP and the Gmail image proxy pre-fetch the pixel, so "opened" is inflated and would mute reminders to people who never read the mail. Opens are still recorded; they gate nothing. Exactly one reminder, `VENDOR_CAMPAIGN_REMINDER_AFTER_MS` (2 days) after the send.
  - **Paced, not blasted**: a rolling-24h `daily_cap` (default 50) with the hourly worker taking `ceil(cap/24)` per sweep (`runCampaignSweep`, awaited separately from the sync `runEmailSweep`). Cold volume burns the same domain reputation verify + RSVP mail depends on.
  - **`paused` is the emergency brake and it stops the reminders too**, not just new invites: halting a campaign because the copy is wrong must not let the second wave go out anyway. `done` (everyone written to) is the normal end state and deliberately does NOT stop reminders those sends are still owed.
  - **Language follows the listing's country**, resolved by `curatedCountry()` (city ", XX" suffix → Slovak/Austrian id sets → HU). HU gets Hungarian, everywhere else English, via the new `SendTarget.guestLocale`. The subject is per-kind, so the payload carries `locale` and the builder picks.
  - **`email_optouts` is address-keyed suppression**, permanent and cross-campaign, because `email_preferences.lifecycle_opt_out` is keyed by `users.id` and this cohort has no user row. **Campaign mail no longer offers any way into it** (owner decision, 2026-07-28): no body link, and no `List-Unsubscribe` header, since `SendTarget.listUnsubscribeUrl` and the outreach branch in `send.ts` are gone. Only lifecycle mail still carries the RFC 8058 pair. The table itself, the `isOptedOut` check before every send, and the `/api/emails/optout-*` routes all STAY: the ~19 addresses that already opted out must never be mailed again, and mail already sitting in inboxes still links to those routes. Guarded by `backend/tests/api/email_integrity.e2e.test.ts` ("campaign mail offers no exit").
  - Covered by `backend/tests/api/vendor_campaign.e2e.test.ts`. That suite deliberately does NOT call `wipeAll()` per test (it drops `users`/`sessions`, costing a ~2s argon2 re-registration each time) and always drains raw `fetch` bodies, since an unread body holds its keep-alive connection and stalls the next request.
- **Campaign schedules (the standing plan):** one `campaign_schedules` row per campaign FAMILY (`vendor_claim` / `vendor_review` / `onboarding`), seeded at boot from `CAMPAIGN_SCHEDULE_RECIPES` in `shared/campaign_schedules.ts`. Every `interval_days` the hourly sweep (`prepareDueSchedules` at the top of `kickCampaignSweep`) builds that family's next campaign **paused, with targets resolved**, so the operator's whole job is Run on `/app/admin/campaigns?tab=plan` (`auto_start` removes even that). Design points:
  - **Personal-invite has no schedule** on purpose: its audience is an imported CSV, so "compose the next one" has no meaning.
  - **The cooldown is what makes repeat safe.** Every family's targeting only excludes addresses THIS campaign wrote to, so a second campaign would re-mail everyone who ignored the first. `prepareSchedule` copies a `status='skipped'` tombstone into the new campaign for every address the family mailed inside `cooldown_days` (180 / 120 / 60), which turns that per-campaign exclusion into a cross-campaign one **without touching a single targeting query**. `min_targets` makes a thin segment wait instead of minting a 4-address campaign.
  - **One in flight per family.** A schedule never builds on top of a campaign it built that hasn't retired (`status != 'done'`), whether it is unrun or mid-send: two paced queues would split one audience and double the hourly rate.
  - The operator knobs are `enabled` (repeat), `interval_days`, `daily_cap`, `auto_start` — nothing else, and `cooldown_days` / `min_targets` are deliberately recipe constants, not columns, because they protect the sending domain rather than express a preference. Shortening the interval re-bases `next_due_at` off `last_prepared_at`, so it takes effect now.
  - Adding a fifth family = one `KindAdapter` entry in `domain/campaign_schedules.ts` + one recipe. Covered by `backend/tests/api/campaign_schedules.e2e.test.ts`.
- **Every campaign family measures opens + clicks, the same two columns and the same way.** `<family>_campaign_sends.opened_at` (tracking pixel) and `.clicked_at` (a `/r/...` redirect), both first-wins via COALESCE, both stamped from a `<sendId>.<hmac>` token with a per-purpose HMAC so a pixel token can't be replayed as a click. Personal-invite and onboarding shipped without either and were attributed only by the conversion join at the far end, which cannot tell a bad subject line (nobody opened) from a bad landing page (everybody clicked, nobody signed up). Rules that must survive later edits: **the redirect always hands over to the same UTM'd destination the mail used to link to directly**, so acquisition attribution never depends on the tracking working; **a forged or unknown token still returns a pixel / still redirects somewhere sane**, never a 4xx, because a mail client is on the other end; and **opens gate nothing**, per the claim-campaign note above — Apple MPP and the Gmail image proxy inflate them, so they are a ceiling, not a readership number. The onboarding click token additionally encodes WHICH wave was clicked (two HMAC purposes, `click` / `click_reminder`), because that family sends two mails against one row and the destination's `utm_content` differs. Cross-family rates are on `/app/admin/analytics`; per-campaign counters on each campaign's admin page.

## What NOT to do

- Don't add a UI library (Radix, MUI, shadcn). The design system is hand-rolled.
- Don't add Redux / Zustand. Provider stack + `localStorage` is enough.
- Don't add react-query. The single API client + React state is enough.
- Don't add Zod / io-ts. TS is the contract; hand-write boundary guards.
- `users.locale` is captured at signup (post-international-expansion) — surfaced on `/api/auth/me` and used by the frontend to override navigator.language detection on fresh devices. The local locale switcher still wins on the device where the user flipped it. **Outbound email renders per-recipient locale** (`backend/src/domain/emails/template.ts`): `recipientLocale="hu"` → single HU card, `"en"` → single EN card, `null` → the legacy bilingual HU-hero + EN-below fallback. `send.ts` resolves it from `users.locale` (`lookupUserLocale`), or `pending_signups.locale` for the pre-verify welcome mail, via `normalizeRecipientLocale`: `hu`/`hu-*` → HU, anything else (incl. DE/FR/ES) → EN, absent → `null`. So a non-HU registrant (signed up through the EN interface → `locale="en"`) gets a clean English single-language email from the first verify mail onward; the bilingual stack now only fires for unknown-locale recipients — guests (no per-guest locale yet) and legacy `null`-locale users. Note: only HU vs EN copy exists — real per-country language (German mail to a DE couple, etc.) is still a follow-up.
